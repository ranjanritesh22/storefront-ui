## Overriding this component

The same `ProductCard`, styled three different ways — cheapest override layer first. Full
model: [docs/overriding.md](../../../../../docs/overriding.md).

### 1. Tokens — rebrand every card at once

Everything `Card` / `Price` / `Badge` / `Button` already read — override on `:root` or scoped
under `[data-theme]` / `[data-brand]`.

<Canvas of={ProductCardStories.OverrideTokens} />

### 2. `productCardVariants` / `productCardLayoutVariants`

`productCardVariants` controls the image aspect ratio (`square` / `portrait` / `landscape`).
`orientation` (`vertical` / `horizontal`) switches the whole card between the default stacked
layout and a horizontal list-item row — this is what `ProductListItem` sets internally.

### 3. `classNames` — reach a specific part

A slot map: `root`, `image`, `body`, `subtitle`, `title`, `price`, `badge`, `rating`, `colors`,
`wishlist`, `quickView`, `swatches`, `swatch`, `cta`.

### Quick view, wishlist, and variant swatches

The wishlist toggle shows only when `onWishlistToggle` is given; the quick-view action (in
vertical layout only — it would overlap the content column in horizontal/list layout) shows only
when `onQuickView` is given; the swatch row shows only when `swatches` (or `product.swatches`) is
non-empty. Each is opt-in by prop presence, matching the CTA and badge.

<Canvas of={ProductCardStories.OverrideClassNames} />

### 4. `slots` — replace one part, keep the rest

Swap any part of the composition while the rest stays exactly as-is — here the `Badge` slot
renders with a different variant without touching the image, title, price, or CTA.

<Canvas of={ProductCardStories.OverrideStructural} />

## Domain-agnostic props: the `product` prop and adapters

`ProductCard` accepts either individual props (`title`, `imageSrc`, `imageAlt`, `price`, ...) or
a single `product` prop typed as `ProductSummary` — a minimal, backend-agnostic shape this
package owns and exports. `ProductSummary` is not shaped like any commerce backend's response;
this package has no data-fetching or backend-types dependency (see ARCHITECTURE.md §1 and
CLAUDE.md's "Domain-agnostic props" rule). You map your API response onto it once, in your own
code — never inside this package:

```ts
import type { ProductSummary } from "@storefront/ui";

// Example: adapting a SAP Commerce Cloud (OCC) product response.
// occProduct's actual shape depends on your OCC config — this is illustrative.
function fromOccProduct(occProduct: OccProduct): ProductSummary {
  return {
    id: occProduct.code,
    name: occProduct.name,
    price: occProduct.price?.value ?? 0,
    currency: occProduct.price?.currencyIso,
    originalPrice: occProduct.discountedPrice?.value,
    image: {
      src: occProduct.images?.find((img) => img.format === "product")?.url ?? "",
      alt: occProduct.name,
    },
    url: `/product/${occProduct.code}`,
    badge: occProduct.badges?.[0]?.label,
    rating: occProduct.averageRating
      ? { value: occProduct.averageRating, count: occProduct.numberOfReviews }
      : undefined,
    colorsCount: occProduct.variantOptions?.length,
    inStock: occProduct.stock?.stockLevelStatus === "inStock",
  };
}

<ProductCard product={fromOccProduct(occProduct)} onCtaClick={() => addToCart(occProduct.code)} />;
```

An individual prop always wins over the matching `product` field, so you can mix: pass
`product` for the bulk of the data and override just `ctaLabel` or `badgeLabel` per instance.
